## 单体架构与微服务架构

> 小故事：以2012年为分界线，在此之前使用**单体架构**，全部代码放一块，打包成一个应用直接部署。2012年**微服务架构**被正式分享后火爆全球，很多企业跟风。但是把一个微信小程序拆成多个部分是不合理的，维护困难（大炮打蚊子？）于是在2019年，对盲目追求微服务架构的讽刺达到高潮，这也被称为鸡汤年。

如果说单体架构是一家大饭店，微服务架构就是有很多小摊的美食街广场

### 微服务架构

#### 好处

1. **技术的异构性**：这意味着每一个团队都可以使用不同的语言。浅显的来说，高性能用Go，大量数据算法用python，想要稳定核心成熟生态用Spring Boot
2. **极致的扩展性**：局部坏死不影响全身

#### 原则

1. 独立开发
2. 独立部署：每个团队对自己的部分拥有100%控制权
3. 独立存储：每个微服务有自己的数据库，不可以跨部门查询，只能访问api去请求，因为每个都是独立的。

但是是一般大厂再用啦~

微服务架构是一种分布式系统，但分布式系统不一定是微服务架构。可以这样理解：微服务架构（话剧）是一种分布式系统（大舞台）。

#### 分布式

假设一个超级厉害的建筑公司，在世界各地都有分部。分布式主要解决五个问题：

1. 如何给世界各地的建筑师天才分配任务？	负载均衡
2. 如何相互沟通交换图纸？			网络通信
3. 一个建筑师生病了怎么办？          容错、高可用
4. 如何确保他们的设计规范是最新版本？      配置管理
5. 如何追踪一个复杂的设计方案是谁在哪里出了错？   分布式追踪

### 单体架构

Apache是一种服务器，这个要知道。

#### 前后端分离演变

又名：从巨石时代走向美丽新世界

2005年左右，前后端没有分离，PHP在Apache里把前后端一起写。

2004–2010：标准化前后端分离阶段，REST、JSON、SPA 大规模落地。

AJAX 诞生，异步通信登场。Asynchronous（异步）：发送请求的时候不用阻塞页面，后台悄悄和服务器通信，拿到数据后局部刷新页面。啊啊，终于不用提交请求之后整个页面卡死等待服务器返回，收到响应整页刷新啦！

数据格式演变：XML → JSON（JavaScript Object Notation）天生适配 JS 解析

REST架构风格：客户端可以请求什么资源？使用什么 HTTP 方法发起请求（GET 查 / POST 新增）？服务器返回数据格式？

负载均衡：把用户流量分发、分担到多台后端服务器，防止单台服务器压力过大

2015–至今：全面爆发。

RESTful API 缺陷：数据过载，多次请求。“我点了名，但是你怎么把信息都给我了，太多了。。。”    GraphQL应运而生：前端决定拿什么数据，后端精准返回。（也许GraphQL是未来？）

前端工程化的四驾马车：

1. 包管理器 NPM / Yarn（一个巨大软件商店）。
2. 构建工具 ：webpack打包 JS、CSS 等各类资源，解决浏览器版本兼容问题，独立开发。
3. 框架库。
4. 编译器 / 转译器。

## 后端发展

> Spring全家桶，也许这也是一个故事会？

在Spring之前，喝水还要挖井，不妥不妥，我们想要渴了时水龙头自动出水，Spring带来“控制反转”loc！

不同的权限散落在不同的系统中，好麻烦，Spring带来“面向切面编程”AOP!

可是强大如Spring也有缺点。

Spring mvc强大但难以部署，版本号不对就只能痛哭。我们希望“约定优先于配置”（要是有专业人士配一个通用版本就好了，其实也不用个我最好的跑车零件自组装，给我一个通用的普通车就行），Spring Boot出现解决了问题，实现了这样的幻想。他也为之后的“微服务打下基础”。
