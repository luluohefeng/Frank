## 单体架构与微服务架构

> 小故事：以2012年为分界线，在此之前使用**单体架构**，全部代码放一块，打包成一个应用直接部署。2012年**微服务架构**被正式分享后火爆全球，很多企业跟风。但是把一个微信小程序拆成多个部分是不合理的，维护困难（大炮打蚊子？）于是在2019年，对盲目追求微服务架构的讽刺达到高潮，这也被称为鸡汤年。

如果说单体架构是一家大饭店，微服务架构就是有很多小摊的美食街广场

### 微服务架构

#### 好处

1. **技术的异构性**：这意味着每一个团队都可以使用不同的语言。浅显的来说，高性能用Go，大量数据算法用python，想要稳定核心成熟生态用Spring Boot
2. **极致的扩展性**：局部坏死不影响全身

#### 原则

1. 独立开发
2. 独立部署：每个团队对自己的部分拥有100%控制权
3. 独立存储：每个微服务有自己的数据库，不可以跨部门查询，只能访问api去请求，因为每个都是独立的。

但是是一般大厂再用啦~

微服务架构是一种分布式系统，但分布式系统不一定是微服务架构。可以这样理解：微服务架构（话剧）是一种分布式系统（大舞台）。

#### 分布式

假设一个超级厉害的建筑公司，在世界各地都有分部。分布式主要解决五个问题：

1. 如何给世界各地的建筑师天才分配任务？	负载均衡
2. 如何相互沟通交换图纸？			网络通信
3. 一个建筑师生病了怎么办？          容错、高可用
4. 如何确保他们的设计规范是最新版本？      配置管理
5. 如何追踪一个复杂的设计方案是谁在哪里出了错？   分布式追踪

谷歌的三篇论文火爆世界，引领了大型分布式系统的构建：

- GFS 存储
- MapReduce 如何在海量廉价计算机上并行计算
- BigTable 支持海量数据库

亚马逊最早把分布式基础设施“云服务AWS”对外售卖，嗯，我们也不难想象why贝索斯成为世界首富。

分布式系统的优点：资源共享+高性能计算；地理分布，就近访问、低延迟。

### 单体架构

Apache是一种服务器，这个要知道。

#### 前后端分离演变

又名：从巨石时代走向美丽新世界

2005年左右，前后端没有分离，PHP在Apache里把前后端一起写。

2004–2010：标准化前后端分离阶段，REST、JSON、SPA 大规模落地。

AJAX 诞生，异步通信登场。Asynchronous（异步）：发送请求的时候不用阻塞页面，后台悄悄和服务器通信，拿到数据后局部刷新页面。啊啊，终于不用提交请求之后整个页面卡死等待服务器返回，收到响应整页刷新啦！

数据格式演变：XML → JSON（JavaScript Object Notation）天生适配 JS 解析

REST架构风格：客户端可以请求什么资源？使用什么 HTTP 方法发起请求（GET 查 / POST 新增）？服务器返回数据格式？

负载均衡：把用户流量分发、分担到多台后端服务器，防止单台服务器压力过大

2015–至今：全面爆发。

RESTful API 缺陷：数据过载，多次请求。“我点了名，但是你怎么把信息都给我了，太多了。。。”    GraphQL应运而生：前端决定拿什么数据，后端精准返回。（也许GraphQL是未来？）

前端工程化的四驾马车：

1. 包管理器 NPM / Yarn（一个巨大软件商店）。
2. 构建工具 ：webpack打包 JS、CSS 等各类资源，解决浏览器版本兼容问题，独立开发。
3. 框架库。
4. 编译器 / 转译器。

## 后端发展

> Spring全家桶，也许这也是一个故事会？

在Spring之前，喝水还要挖井，不妥不妥，我们想要渴了时水龙头自动出水，Spring带来“控制反转”loc！

不同的权限散落在不同的系统中，好麻烦，Spring带来“面向切面编程”AOP!

可是强大如Spring也有缺点。

Spring mvc强大但难以部署，版本号不对就只能痛哭。我们希望“约定优先于配置”（要是有专业人士配一个通用版本就好了，其实也不用个我最好的跑车零件自组装，给我一个通用的普通车就行），Spring Boot出现解决了问题，实现了这样的幻想。他也为之后的“微服务打下基础”。

这时，我们很容易意识到一个问题：“全栈开发”太自由，太依赖个人能力和团队规范。微软Typescript虽然尝试解决问题，但一些企业更偏爱“Spring Boot + Spring Cloud”的Java黄金组合。

我们对比一下Node.js 和 Spring(Java):

- Node.js适合I/O密集、快速迭代的小公司，像快艇。
- Spring更稳定，启动慢，转头也慢，像航母。（银行就很喜欢）

但他们的差距在减小。

你可能会问：Python在哪里，怎么没见你提到？

Python更多用于数据分析，AI，而不太适合高并发后端业务和Web开发，一个是因为性能偏低，另一个是因为有GIL（全局解释器锁）：同时在一个进程内只能走一个线程。

但你非要用也不是不可以，像Django,Flask这样的Web框架生态已经很成熟啦。Instagram就是一个成功案例。

## 云原生浪潮和现代工程化

### 四、容器化技术

环境不一致很痛苦，想象一下，你的程序在Mac本地正常跑，部署到Linux服务器上就因为环境不一致直接报错。

最早的解决方案是用VM虚拟机，环境隔离是爽了，但是笨重、性能损耗大。因为每台虚拟机自带完整操作系统，资源开销高。

2013年Docker（容器）诞生。巧妙利用Linux内核空间，很夸张，一台物理机上可以运行上千个容器。

哇塞，那到时候成千上万的容器你怎么调度编排呢？Google开源的Kubernetes（也可以叫k8s）在本次三国杀中成为赢家。核心理念是声明式。你只用写文件声明你期望是什么状态，k8s的控制循环就会自动比对，自动扩缩容、故障自愈。

## 六、CI/CD   DevOps

CI   持续集成

CD   持续交付/部署

DevOps = Dev（开发） + Ops（运维），核心理念是“你构建，你运行”。解决了开发和运维相互打架的“筒仓效应”。依靠CI和CD这两个基石。

Go语言也出现。支持跨平台编译，为容器化而生，是云原生和高并发的不二之选。（尤其是直播服务，很需要Go）

至此，微服务的三驾马车已经备齐：

1. 微服务架构：业务拆分
2. 云原生（Docker + K8s）：容器 + 编排
3. DevOps（CI/CD流水线）

## 八、Serverless与边缘计算的趋势与未来

### Serverless

到这里我就简单写了，因为越来越复杂，未来也有许多不确定性。

到现在，个人开发者不要自己买实体物理机（物理服务器）放家里，中小型企业也不这么干了，很抽象啊，你去阿里云、腾讯云、AWS或者Google Cloud去租一个啊。

Serverless出现就是说：你开发者就好好写代码去，别在乎运维，你只要写出核心业务逻辑，告诉我在什么情况下执行。至于需要多少服务器、怎么运行、怎么扩容，服务器怎么配置才能达到要求，都不是你该操心的，平台会帮你搞定。

缺点：冷启动，实例用完即丢，测试困难。
